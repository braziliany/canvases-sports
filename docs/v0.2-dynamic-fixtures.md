## Fixtures Schema

根结构：

```json
{
  "schemaVersion": 1,
  "league": {},
  "updatedAt": "2026-08-22T11:48:00+08:00",
  "source": {},
  "fixtures": []
}
```

Fixture：

```json
{
  "id": "2026-regular-w19-changzhou-wuxi",
  "round": 19,
  "date": "2026-08-29",
  "time": "19:40",
  "homeTeam": "常州",
  "awayTeam": "无锡",
  "homeScore": null,
  "awayScore": null,
  "status": "scheduled",
  "venue": null
}
```

字段约定：

| 字段 | 规则 |
| --- | --- |
| `id` | 非空、全局唯一、稳定，不随展示文字变化 |
| `round` | 正整数；江苏联赛表示官方赛程周 |
| `date` | 严格 `YYYY-MM-DD`，必须是真实日历日期 |
| `time` | 严格 `HH:mm`，24 小时制 |
| `homeTeam` / `awayTeam` | 非空且不能相同 |
| `homeScore` / `awayScore` | `scheduled`、`postponed`、`cancelled` 时均为 `null`；`finished` 时均为非负整数；`live` 时两者同时为空或为非负整数 |
| `status` | 只允许统一状态枚举 |
| `venue` | 字符串或 `null`；未知时不猜测 |

`fixtures` 必须按 `date + time` 升序排列。同一开球时间允许多场比赛，顺序再由稳定 `id` 确定。

## 状态映射

统一状态：

| 来源文本 | 统一状态 |
| --- | --- |
| 未开始、待赛、已安排 | `scheduled` |
| 进行中、中场 | `live` |
| 已结束、完赛 | `finished` |
| 延期、推迟 | `postponed` |
| 取消 | `cancelled` |

未知来源状态必须报错，不能自动降级为 `scheduled`。

## 真机状态矩阵验证

### 状态映射

| `status` | 展示 |
| --- | --- |
| `scheduled` | 未开始 |
| `live` | 进行中 |
| `finished` | 已结束 |
| `postponed` | 延期 |
| `cancelled` | 已取消 |

### 比分规则

比分展示与状态展示解耦：状态只决定状态文本，比分只由两个比分字段是否完整决定。

```text
如果 homeScore 与 awayScore 都有值
    displayScore = homeScore + " : " + awayScore
否则
    displayScore = "VS"
```

`0` 是有效比分，不能使用数值真假判断“是否有值”。只要任意一个比分为缺失值（当前合同中为 `null`），就显示 `VS`，不展示半个比分。

真机已确认：

- `常州 1 : 0 苏州 / 进行中`；
- `盐城 2 : 2 南通 / 已结束`；
- `scheduled`、`postponed`、`cancelled` 不错误展示比分；
- `live` 且比分缺失时显示 `VS / 进行中`。

### Shortcut 结构结论

稳定结构是先分别得到 `displayStatus` 与 `displayScore`，再写入模板字段。不要先由比赛状态推导 `hasScore`，也不要让状态分支承担比分格式化。

```text
status → 状态映射 → displayStatus

homeScore + awayScore
→ 两者都有值？
   ├─ 是："homeScore : awayScore"
   └─ 否："VS"
→ displayScore

displayStatus + displayScore
→ Chained Update View
→ Final match-row
```

这不会改变 ADR-006 的链式 View Update：字段计算可以彼此独立，最终对 Created View 的更新仍必须逐步传递前一个 Updated View。

## Less is More 设计原则

> 状态归状态，比分归比分。有完整比分就显示比分，没有就显示 `VS`。

- 优先按字段事实直接生成展示值，不从无关状态间接推导。
- 将每个条件限制在一个职责内，避免嵌套 If、跨层 `如果的结果` 和只为传递而存在的中间变量。
- 只有在多个下游确实复用时才引入 `hasScore`；单一展示点直接判断两个比分是否完整。
- 先保证数据流可读、可 Quick Look、可逐段验证，再增加视觉或业务分支。
- 新条件必须来自明确需求或数据合同，不为“可能以后会用”预先增加分支。

## Shortcut 实现基线

设备阶段沿用 v0.1：获取 `fixtures` → `Repeat with Each` → 创建 `match-row` → 每次 Update 显式接收前一个 View 输出 → 每轮返回 Final Updated View → `Repeat Results` 写入 Grid Children。状态与比分矩阵已在真机验证，当前成功行为保持冻结。
