原则：机器处理确定性事实并发布，人只处理不确定性；No evidence is better than wrong evidence。

## 2026-08-31

### v0.2 Integration Fix · Candidate Test Isolation

- Integration Review 发现：合法 Candidate 写入正式候选文件后，`results:confirm` 的确认前全套测试因硬编码候选数量为 0 而失败。
- Candidate 单元测试改用独立内存基线，不再把正式候选文件当前状态作为测试前提。
- 会随结算变化的 fixtures/standings 单元测试同样改用隔离基线，正式文件仅承担合同完整性检查。
- 正式数据完整性测试改为验证 schema、fixture 关联、确认审计一致性和明确测试/mock 标记。
- 空集合、单条待审核、多条待审核、已确认 Candidate 均为合法业务状态；非法比分、状态、时间与重复 ID 仍被拒绝。
- 保留 `results:confirm` 的确认前验证与完整测试门禁，不修改 Candidate、settlement、standings 或事务合同。
- Windows 真机 CLI 回归中，嵌套并行 test workers 出现 `0xC0000409`；确认门禁改为逐个直接执行全部 `*.test.js`，仍在写入前覆盖完整测试集。
- 真实多文件提交回归发现默认 `copyFile` 误接收条目索引 `1` 并将其解释为 `COPYFILE_EXCL`；默认替换器现忽略注入测试专用 index，并新增成功多文件提交测试。

测试原则：测试验证业务合同，不依赖生产数据当前恰好为空。合法 Candidate 的存在是正常业务状态，不是测试污染。

### v0.2 Phase 5 · Result Adapter / 自动赛果发现层

- 保存扬子晚报/紫牛新闻第 19 周最终战报的最小来源快照，记录来源 URL、等级、获取时间和比赛上下文。

- 新增 `npm run results:discover -- --dry-run`，预览发现的 Candidate；非 dry-run 仍要求精确 `ADD`，且只写 candidate 文件。

数据层级保持：Observation → Candidate → Human Review → Authoritative Fact → Derived Data → Renderer。

原则：机器负责发现 Observation，人负责确认 Authoritative Fact。自动化处理机械工作，人处理不确定性。

### Candidate Isolation Safety Final Fix

- Integration 回归暴露出 shell 临时目录切换失败后，CLI 仍按脚本位置访问正式 data 的操作风险。
- 三条赛果 CLI 新增共享的显式 `--isolated-data-dir` 解析；只接受已存在的绝对目录，并拒绝正式 data。
- 缺失参数、相对路径、无效目录或正式目录冒充隔离目录均在读取数据前失败，不允许 fallback。
- 回归测试改用 Node `fs.mkdtemp` 和内部清理，覆盖无效路径、缺失参数、真实隔离 ADD、重复发现和无事务残留。
- 原则：隔离失败必须显式失败，不能回退到正式数据路径。

### v0.2 Phase 4 · ResultCandidate 人工录入

- 新增 `npm run results:add`，从正式 fixtures 选择 scheduled/live 比赛并录入候选赛果。
- 比分严格接受非负整数，0 合法；来源必填，来源 URL 可空且非空时只接受 HTTP/HTTPS。
- Candidate ID 使用 fixture ID 与 UTC 观察时间生成；碰撞时增加数字后缀，不覆盖旧记录。
- 同一比赛已有未审核 Candidate 时展示详情，并要求输入 `MORE` 才能继续新增另一来源。
- 写入前展示完整 Preview；只有精确输入 `ADD` 才写候选文件。
- 复用现有 JSON 事务写入；add 不修改 fixtures、standings，也不自动 confirm/build。
- 测试 mock 没有进入正式 candidate 文件。

数据层级：Observation → Candidate → Confirmed Fact → Derived Data → Renderer。不要把 Observation 直接写成 Fact。

## 2026-08-30

### v0.2 Phase 3 · Match Result Ingestion

- 新增稳定的 ResultCandidate 契约和空的正式候选文件；候选必须记录比赛、比分、来源、采集时间和审核状态。
- 新增 `npm run results:confirm -- <candidateId>` 人工确认入口，只有输入 `CONFIRM` 才进入结算。
- 确认后在内存中应用权威 finished、重建 standings、校验全部合同并运行完整测试；通过后才提交正式文件。
- 同比分重复确认幂等；不同比分明确 conflict；postponed/cancelled、球队不匹配和非法比分全部拒绝。
- 多文件写入中途失败会恢复 fixtures、standings 和候选审计文件，避免半完成状态。
- 三场 2026-08-29 对阵只使用 mock candidate 做结构回归，没有猜测或污染正式赛果。

关键原则：自动化处理机械工作，人只负责提供机器无法可靠判断的事实。`effectiveStatus` 属于运行展示层，原始 `status` 属于权威事实层。

- 只结算原始 status=finished 且双方比分完整的正式赛程；effectiveStatus 不确认完赛。
- 覆盖胜平负、进失球、净胜球、积分、排名、0:0、状态过滤、缺失比分和幂等测试。
- 从 2026-08-15 官方快照作为不可变过渡基线，叠加其后的明确赛果；当前三场尚未 finished，因此正式 standings 语义不变。
- 实现官方同分规则的头对头前三项和总净胜球/总进球；公平竞赛与抽签资料缺失时拒绝伪排名。

关键原则：赛程是事实源，积分榜是派生数据。完整历史 fixtures 回填后移除过渡基线，不分别手工维护赛果与积分榜。

### v0.2 Dynamic Fixtures · 真机验证与冻结

完成：

- 使用独立的 `data/fixtures-device-test.json` 完成六种状态矩阵真机验证，正式 `data/fixtures.json` 未被测试数据污染。
- 验证 scheduled、live、finished、postponed、cancelled 的中文展示，以及 live 比分缺失容错。
- 验证完整比分显示 `主队比分 : 客队比分`；任一比分缺失时显示 `VS`。
- 真机确认 `常州 1 : 0 苏州 / 进行中` 与 `盐城 2 : 2 南通 / 已结束`。
- 将设备夹具纳入离线测试与 `npm run validate`。

关键结论：

- 状态归状态，比分归比分；不要让状态分支决定比分格式。
- `0` 是有效比分，必须检查值是否存在，不能使用数值真假判断。
- 避免为单一展示点堆叠嵌套 If、`hasScore` 和跨层“如果的结果”。
- 计算逻辑保持最小化，不改变 ADR-006 的链式 View Update。

冻结：v0.2 状态与比分渲染真机验证完成；后续扩展不应改动当前成功数据流，除非发现明确错误或出现新合同需求。

- v0.1 只声明四字段动态积分榜 PoC 完成。
