# v0.2 Production Data Sync

## Production flow

```text
Trusted online sources → Fetch → stable snapshots → source adapters
→ ResultObservation → exact fixture match → conservative reconciliation
→ existing ResultCandidate → existing settlement → authoritative fixtures
→ shared standings builder → validation + tests → GitHub Raw → Shortcut → Canvases
```

`npm run results:sync -- --dry-run` performs the online fetch and complete in-memory preparation without writing. `npm run results:sync` writes changed snapshots, candidates, fixtures, and standings through the existing rollback-capable JSON transaction layer. Adapters never fetch and the fetch layer never interprets match results.

## Reconciliation policy

- One `official` source, unique match and no trusted conflict: `AUTO_SETTLE`.
- Two independent `official-republish` / `trusted-media` publishers with the same score and no conflict: `AUTO_SETTLE`.
- One non-official source, conflict, invalid provenance/score, parse failure, no match or ambiguous match: `NEEDS_REVIEW` or hard failure; no authoritative write.

Duplicate observations do not increase evidence count. Human fallback remains `results:add` / `results:confirm`.

## GitHub Actions and failure safety

`.github/workflows/result-sync.yml` supports manual dispatch, development-branch push validation, and a Saturday 30-minute match-window schedule. With only `contents: write`, it runs sync, the shared builder, validation, full tests and whitespace checks, then commits only changed `data/`. It never force-pushes or merges. GitHub only exposes `workflow_dispatch` after a workflow exists on the default branch, so the pre-merge development acceptance uses the branch-scoped push trigger.

Fetch/parse failure stops before a transaction. Unsafe matching or insufficient evidence cannot settle. Validation/test failure prevents Action commit/push. Multi-file writes retain the existing rollback guarantee; this is not a claim of native cross-file filesystem atomicity.

> No evidence is better than wrong evidence.
