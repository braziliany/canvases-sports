# 决策记录

## ADR-001：Canvases 不直接抓取赛事网页

原因：官方正文为图片，HTML 和图片路径均可能变化，且未来多个客户端需要复用数据。

决定：增加 Adapter 层，客户端只依赖经验证的统一 JSON。

## ADR-002：未知趋势不伪造

原因：官方快照未提供 previous rank，单靠当前表不能推导可信趋势。

决定：`previousRank` 与 `trend` 均为 `null`，UI 显示 `—`。

## ADR-003：先提供平台无关 View Model

状态：Superseded by ADR-005。

原因：现有资料无法唯一识别 Canvases 产品和 API。

决定：不根据 Scriptable 猜测 API；先完成经过测试的数据层和 Web 参考 UI，待官方文档到位后只新增 Renderer。

## ADR-004：Canvases Native Renderer 必须以真实 App 资料为依据

状态：Superseded by ADR-005。

原因：目标产品已通过 TestFlight 邀请确认，但公开页面没有运行时、组件、网络、存储或项目格式文档。将 Scriptable 或 SwiftUI 的名称套入 Canvases 会产生不可验证实现。

决定：保留现有 Unified View Model 和 Web Reference Renderer，不创建猜测性原生代码。拿到新建项目默认代码、Network/Layout 文档或官方 Sample 后，先完成 Hello World 与 HTTP JSON Probe，再实现 Native Renderer。

编号说明：ADR-002 已用于“未知趋势不伪造”，为保持决策历史稳定，本决策使用 ADR-004。

## ADR-005：Shortcuts-driven Canvases architecture

状态：Accepted。

### Context

用户提供的官方 Canvases User Guide 摘要确认：Canvases 使用 Visual Editor 创建 Widget，通过 Shortcuts Actions 更新具有稳定 ID 的 Views，并明确没有需要编写的应用内代码。

### Decision

采用：

```text
GitHub standings.json
        ↓
iOS Shortcuts
        ↓
Canvases Views / Grid Template
        ↓
Widget
```

Web Reference Renderer 仅用于调试、数据校验和桌面预览。

### Consequences

优点：

- 符合官方工作流；
- 不引入虚构 Runtime；
- 可利用 Shortcuts Automation；
- Canvas 专注布局，数据层继续复用。

限制：

- iOS Widget 刷新受系统预算影响；
- Shortcut 是运行依赖；
- Canvas 设计、Shortcut 构建和验证主要需要真机操作；
- 网络/校验失败时依赖“不替换现有 Views”保留最后成功画面。

编号说明：任务建议使用 ADR-003，但该编号已存在。为保持历史引用稳定，不重编号旧决策，本决策使用 ADR-005。

## ADR-006：Template View Update 采用不可变链式传递

状态：Accepted and device-verified。

### Context

真机调试曾出现 13 行全部显示同一球队的情况。Quick Look 已确认每轮 JSON 字段不同，问题位于 Created View 的引用关系。

### Decision

每个 `Update View Created from Template` 必须接收前一个 Update 输出的 View。每轮 Repeat 的最后结果必须是完成全部字段更新的根 View；`Repeat Results` 再作为 `standings-grid.Children` 的完整值。

```text
Create View → Update rank → Update team-name
→ Update goal-difference → Update points → Final View
```

禁止从同一个初始 Created View 并行更新多个字段，也不依赖动作的视觉排列推断 View 输入。

### Consequences

- 动态模板字段可以稳定保留在同一最终 View 中；
- `Repeat Results` 可直接形成 13 行最终 View 列表；
- 后续动态赛程等 Template 项目必须复用该链式规则；
- Quick Look 与显式命名变量成为标准排错手段。

## ADR-007：赛程状态与比分展示解耦

状态：Accepted and device-verified。

### Context

v0.2 真机测试曾将比分展示与比赛状态高度耦合，形成多层 If、`hasScore` 和跨层“如果的结果”传递。结构复杂后，状态映射、比分完整性与 View 更新难以分别排查。

### Decision

有效状态（现由 `effectiveStatus` 提供）只映射 `displayStatus`；比分只根据 `homeScore` 与 `awayScore` 是否同时存在生成 `displayScore`：两者完整时显示 `主队比分 : 客队比分`，任意一个缺失时显示 `VS`。`0` 是有效比分。

```text
effectiveStatus → displayStatus
homeScore + awayScore → displayScore
displayStatus + displayScore → Chained Update View
```

不根据 `scheduled`、`live`、`finished` 等状态推断是否显示比分。只有多个下游需要复用时才引入 `hasScore`。

### Consequences

- 状态映射与比分容错可以独立验证；
- `live` 可同时支持有比分与比分缺失；
- 减少嵌套条件和脆弱的 Magic Variable 传递；
- ADR-006 继续有效：展示值独立计算，但 View 更新仍保持不可变链式传递；
- 形成项目的 Less is More 原则：使用满足已知合同的最小数据流，不为假设场景预建分支。

## ADR-008：Effective Match Status

状态：Accepted。

### Context

2026-08-29 20:53 真机实战发现，19:40 开始的三场比赛仍显示“未开始”。Shortcut、Canvases 更新链和状态文字映射均正常；问题是发布 JSON 的静态 `status: scheduled` 不会随时间自然进入比赛中。

### Decision

保留来源事实 `status`，在 Normalizer / State Logic 中派生供展示消费的 `effectiveStatus`：

- `finished`、`postponed`、`cancelled` 直接覆盖时间推导；
- `live` 保持 `live`；
- `scheduled` 在 `now < kickoff` 时保持 `scheduled`，在 `now >= kickoff` 时派生为 `live`；
- 禁止根据 90 或 120 分钟比赛时长自动派生 `finished`。

`effectiveStatusAt` 记录派生时刻。Shortcut 只读取 `effectiveStatus` 并映射展示文字，不比较当前时间、不计算比赛时长、不纠正状态。

> Explicit state > Derived state.

> Time can start a match, but time alone cannot finish a match.

> Shortcut is a renderer, not a state engine.

### Consequences

- 开球边界可以确定性测试并在发布前标准化；
- 延期、取消和已结束不会被时间错误覆盖；
- 没有可靠赛果时宁可保持 `live`，不制造假的 `finished`；
- 发布流程必须在需要刷新有效状态时重新运行 Normalizer；
- Shortcut 只需将状态输入字段从 `status` 改为 `effectiveStatus`，无需增加业务分支。

## ADR-009：Match Result Settlement and Standings Derivation

状态：Accepted。

### Context

赛程已经有原始状态和比分，但积分榜仍是独立静态文件。若赛果和积分榜分别手工维护，会形成两个可能互相冲突的事实源。与此同时，当前正式 fixtures 只包含 8 月 29 日三场，不能假装拥有完整赛季历史。

### Decision

赛程是赛果事实源，积分榜是派生视图：

```text
fixtures → standings calculator → standings.json → Shortcut → Canvases
```

只有原始 `status === "finished"` 且双方比分均为非负整数的比赛进入结算；`effectiveStatus` 永远不能确认完赛。当前使用 2026-08-15 官方积分榜快照作为不可变历史基线，再叠加其后的 finished fixtures。完整历史赛果回填后移除该基线。

官方同分顺序为相互比赛积分、相互比赛净胜球、相互比赛进球、总净胜球、总进球、公平竞赛积分、抽签。资料不足时 build 必须失败，不得用球队名、当前顺序或通用净胜球规则伪造官方排名。

### Consequences

- 正式赛果只维护一次，standings 可重复生成；
- scheduled/live/postponed/cancelled 与缺失比分不会污染积分；
- 0:0 被正确结算；
- 完整历史赛果、公平竞赛积分和抽签顺序成为明确的数据补全项；
- Shortcut 与 Canvases 模板无需修改，继续消费向后兼容的 standings schema。

## ADR-010：Match Result Ingestion and Human Confirmation

状态：Accepted。

### Context

时间和 `effectiveStatus` 只能表达比赛按赛程应已开始，不能证明比赛已经结束。外部来源给出的比分也可能错误、过时或对应错比赛，因此 candidate 不能直接成为正式 fixture，更不能直接影响积分榜。

### Decision

建立独立的 ResultCandidate 契约和显式人工确认边界：

```text
external/manual observation → ResultCandidate
→ human CONFIRM → authoritative fixture
→ standings build + validation + tests
```

确认必须校验 fixtureId、主客队、非负整数比分和正式状态。`effectiveStatus` 是展示层运行状态；原始 `status` 是事实层权威状态。只有人工确认产生的 `status: finished` 与完整比分具有结算效力。

同一正式比分重复确认是幂等 no-op；不同比分是冲突，禁止静默覆盖。postponed/cancelled 不得直接结算。验证和测试在正式写入前完成，最终 fixtures、standings 与 candidate 审核状态采用临时文件加失败回滚的多文件事务写入。

### Consequences

- 外部 Adapter、人工录入、Hermes 或未来 Worker 都只产生同一个 candidate contract；
- 自动化处理校验、计算和写入，人只确认机器无法可靠判断的赛果事实；
- Shortcut 不承担业务规则，Canvases 不承担数据判断，积分榜不猜比赛结果；
- 实时抓取、轮询、Webhook、Cron 和自动发布继续留在后续阶段。

### Phase 4 clarification

`results:add` 将人工观察写入 Candidate 层，不写 authoritative fixtures 或 derived standings。它复用既有 ResultCandidate schema 和事务写入器；同一 fixture 的多个来源 Candidate 可共存，任何已有记录都不得被覆盖。只有后续独立的 `results:confirm` 和显式 `CONFIRM` 才能跨越 Candidate → Fact 边界。

## ADR-011：Candidate 测试验证合同，不假设正式文件为空

Integration Review 发现确认前全套测试把 `data/result-candidates.json` 当前为空当作不变量。真实流程先创建 Candidate，再运行确认测试，因此该假设会阻断所有合法结算。

决定：Candidate 及会随结算变化的 fixture/standings 单元测试使用独立内存/临时数据。正式文件测试验证 schema、fixture 关联、确认审计一致性和明确测试污染标记，不验证 Candidate 数量或固定比赛状态。空、单条、多条及合法 confirmed 均属于合同允许状态；非法数据仍严格失败。`results:confirm` 的确认前完整测试门禁继续保留，并按测试文件串行执行以避免 Windows 嵌套 worker 崩溃。

端到端回归还发现事务默认回调把条目 index 传入 `copyFile` flags，导致第二个正式文件被误设为 exclusive copy。默认替换器现明确只接收源与目标；index 仅保留给故障注入回调。该修复恢复原设计的多文件事务式提交语义，不改变回滚合同。

> 测试验证业务合同，不依赖生产数据当前恰好为空。

## ADR-012：Automated Result Discovery 保持 Observation 与 Fact 分离

状态：Accepted。

### Context

人工 `results:add` 能安全建立 Candidate，但维护者仍要先自行发现赛果。任意网页抓取或 Adapter 直接写 fixture 会把来源不确定性绕过既有人工确认边界。

### Decision

Phase 5 第一版只支持一个固定结构的扬子晚报/紫牛新闻最终战报快照，来源等级记录为 `official-republish`：

```text
Source → Snapshot → Adapter → ResultObservation
→ Fixture Matcher → ResultCandidate → Human Review
```

Adapter 只解析 Observation；Matcher 必须以 league、season、round、date、homeTeam 和 awayTeam 得到唯一 fixture。零匹配与多匹配均失败。Candidate 继续复用既有 schema、ID 策略和事务层；写入前需要精确 `ADD`，成为权威事实仍需要独立的 `CONFIRM`。

精确重复来源发现跳过；相同比分的不同来源以及不同比分的冲突来源均可共存，不做投票、可信度评分或自动确认。

### Consequences

- 机器开始承担可重复的赛果发现，人工只判断来源与赛果是否可信；
- 单元测试读取固定最小快照，不依赖网页在线可用性；
- fixtures、standings、Shortcut 和 Canvases 合同不变；
- 在线 fetch、定时执行、更多来源和发布编排留给后续阶段。

> 人不负责发现赛果，人只负责确认机器发现的赛果是否可信。

### Isolation safety clarification

测试/回归调用三条赛果 CLI 时必须显式提供 `--isolated-data-dir`。该路径必须是已存在的绝对目录且不能等于正式 `data/`；解析失败立即终止，不根据当前工作目录或失败的外部目录切换回退到正式数据。临时目录由 Node `fs.mkdtemp` 建立和清理。

> 隔离失败必须显式失败，不能回退到正式数据路径。
