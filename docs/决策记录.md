# 决策记录

## ADR-001：Canvases 不直接抓取赛事网页

原因：官方正文为图片，HTML 和图片路径均可能变化，且未来多个客户端需要复用数据。

决定：增加 Adapter 层，客户端只依赖经验证的统一 JSON。

## ADR-002：未知趋势不伪造

原因：官方快照未提供 previous rank，单靠当前表不能推导可信趋势。

决定：`previousRank` 与 `trend` 均为 `null`，UI 显示 `—`。

## ADR-003：先提供平台无关 View Model

状态：Superseded by ADR-005。

原因：现有资料无法唯一识别 Canvases 产品和 API。

决定：不根据 Scriptable 猜测 API；先完成经过测试的数据层和 Web 参考 UI，待官方文档到位后只新增 Renderer。

## ADR-004：Canvases Native Renderer 必须以真实 App 资料为依据

状态：Superseded by ADR-005。

原因：目标产品已通过 TestFlight 邀请确认，但公开页面没有运行时、组件、网络、存储或项目格式文档。将 Scriptable 或 SwiftUI 的名称套入 Canvases 会产生不可验证实现。

决定：保留现有 Unified View Model 和 Web Reference Renderer，不创建猜测性原生代码。拿到新建项目默认代码、Network/Layout 文档或官方 Sample 后，先完成 Hello World 与 HTTP JSON Probe，再实现 Native Renderer。

编号说明：ADR-002 已用于“未知趋势不伪造”，为保持决策历史稳定，本决策使用 ADR-004。

## ADR-005：Shortcuts-driven Canvases architecture

状态：Accepted。

### Context

用户提供的官方 Canvases User Guide 摘要确认：Canvases 使用 Visual Editor 创建 Widget，通过 Shortcuts Actions 更新具有稳定 ID 的 Views，并明确没有需要编写的应用内代码。

### Decision

采用：

```text
GitHub standings.json
        ↓
iOS Shortcuts
        ↓
Canvases Views / Grid Template
        ↓
Widget
```

Web Reference Renderer 仅用于调试、数据校验和桌面预览。

### Consequences

优点：

- 符合官方工作流；
- 不引入虚构 Runtime；
- 可利用 Shortcuts Automation；
- Canvas 专注布局，数据层继续复用。

限制：

- iOS Widget 刷新受系统预算影响；
- Shortcut 是运行依赖；
- Canvas 设计、Shortcut 构建和验证主要需要真机操作；
- 网络/校验失败时依赖“不替换现有 Views”保留最后成功画面。

编号说明：任务建议使用 ADR-003，但该编号已存在。为保持历史引用稳定，不重编号旧决策，本决策使用 ADR-005。

## ADR-006：Template View Update 采用不可变链式传递

状态：Accepted and device-verified。

### Context

真机调试曾出现 13 行全部显示同一球队的情况。Quick Look 已确认每轮 JSON 字段不同，问题位于 Created View 的引用关系。

### Decision

每个 `Update View Created from Template` 必须接收前一个 Update 输出的 View。每轮 Repeat 的最后结果必须是完成全部字段更新的根 View；`Repeat Results` 再作为 `standings-grid.Children` 的完整值。

```text
Create View → Update rank → Update team-name
→ Update goal-difference → Update points → Final View
```

禁止从同一个初始 Created View 并行更新多个字段，也不依赖动作的视觉排列推断 View 输入。

### Consequences

- 动态模板字段可以稳定保留在同一最终 View 中；
- `Repeat Results` 可直接形成 13 行最终 View 列表；
- 后续动态赛程等 Template 项目必须复用该链式规则；
- Quick Look 与显式命名变量成为标准排错手段。

## ADR-007：赛程状态与比分展示解耦

状态：Accepted and device-verified。

### Context

v0.2 真机测试曾将比分展示与比赛状态高度耦合，形成多层 If、`hasScore` 和跨层“如果的结果”传递。结构复杂后，状态映射、比分完整性与 View 更新难以分别排查。

### Decision

有效状态（现由 `effectiveStatus` 提供）只映射 `displayStatus`；比分只根据 `homeScore` 与 `awayScore` 是否同时存在生成 `displayScore`：两者完整时显示 `主队比分 : 客队比分`，任意一个缺失时显示 `VS`。`0` 是有效比分。

```text
effectiveStatus → displayStatus
homeScore + awayScore → displayScore
displayStatus + displayScore → Chained Update View
```

不根据 `scheduled`、`live`、`finished` 等状态推断是否显示比分。只有多个下游需要复用时才引入 `hasScore`。

### Consequences

- 状态映射与比分容错可以独立验证；
- `live` 可同时支持有比分与比分缺失；
- 减少嵌套条件和脆弱的 Magic Variable 传递；
- ADR-006 继续有效：展示值独立计算，但 View 更新仍保持不可变链式传递；
- 形成项目的 Less is More 原则：使用满足已知合同的最小数据流，不为假设场景预建分支。

## ADR-008：Effective Match Status

状态：Accepted。

### Context

2026-08-29 20:53 真机实战发现，19:40 开始的三场比赛仍显示“未开始”。Shortcut、Canvases 更新链和状态文字映射均正常；问题是发布 JSON 的静态 `status: scheduled` 不会随时间自然进入比赛中。

### Decision

保留来源事实 `status`，在 Normalizer / State Logic 中派生供展示消费的 `effectiveStatus`：

- `finished`、`postponed`、`cancelled` 直接覆盖时间推导；
- `live` 保持 `live`；
- `scheduled` 在 `now < kickoff` 时保持 `scheduled`，在 `now >= kickoff` 时派生为 `live`；
- 禁止根据 90 或 120 分钟比赛时长自动派生 `finished`。

`effectiveStatusAt` 记录派生时刻。Shortcut 只读取 `effectiveStatus` 并映射展示文字，不比较当前时间、不计算比赛时长、不纠正状态。

> Explicit state > Derived state.

> Time can start a match, but time alone cannot finish a match.

> Shortcut is a renderer, not a state engine.

### Consequences

- 开球边界可以确定性测试并在发布前标准化；
- 延期、取消和已结束不会被时间错误覆盖；
- 没有可靠赛果时宁可保持 `live`，不制造假的 `finished`；
- 发布流程必须在需要刷新有效状态时重新运行 Normalizer；
- Shortcut 只需将状态输入字段从 `status` 改为 `effectiveStatus`，无需增加业务分支。
