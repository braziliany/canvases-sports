# v0.2 Phase 3 — Match Result Ingestion

## 目标

Phase 3 只解决一个问题：已经获得可信终场比分后，怎样经过人工确认，安全地把它写成正式比赛事实并重建积分榜。

```text
可信来源或未来 Adapter
        ↓
data/result-candidates.json
        ↓ 人工执行 results:confirm 并输入 CONFIRM
authoritative fixtures.json
        ↓
standings calculator
        ↓
standings.json
```

候选数据不能直接参与积分计算。`effectiveStatus` 仍是展示层运行状态；只有正式 fixture 的原始 `status: finished` 和完整比分具有结算效力。

## ResultCandidate contract

```json
{
  "id": "source-and-fixture-specific-id",
  "fixtureId": "2026-regular-w19-changzhou-wuxi",
  "homeTeam": "常州",
  "awayTeam": "无锡",
  "homeScore": 1,
  "awayScore": 0,
  "source": "明确的赛果来源名称",
  "sourceUrl": "https://example.com/result",
  "observedAt": "2026-08-29T22:00:00+08:00",
  "reviewStatus": "candidate",
  "confirmedAt": null
}
```

`sourceUrl` 在人工离线来源无法提供 URL 时可以是 `null`。比分必须是非负整数，因此 `0:0` 合法。`reviewStatus` 当前只允许 `candidate` 或 `confirmed`；确认后必须记录 `confirmedAt`。

文档示例和测试分数均为隔离 mock，不代表 2026-08-29 的真实赛果。正式候选文件可以为空，也可以包含合法的待审核或已确认 Candidate；测试不得依赖其当前数量。

Integration Review 曾发现确认前测试错误地假设正式候选文件必须为空，导致合法 Candidate 阻断 `results:confirm`。修复后，单元测试使用隔离输入，正式数据检查验证 schema、关联、审计状态和污染标记，同时保留确认前完整测试门禁。

真实 CLI 回归同时验证了确认后的 finished fixtures 与 derived standings 不会破坏测试隔离。确认门禁逐个执行完整 `*.test.js` 集合；多文件默认提交修正了条目 index 被误解释为 `COPYFILE_EXCL` 的问题，1:0、0:0、Conflict 与 Duplicate 均通过隔离端到端验证。

## 人工确认

将人工复核过但尚未成为事实的记录加入候选文件并通过 `npm run validate` 后，运行：

```bash
npm run results:confirm -- <candidateId>
```

命令会显示对阵、开球时间、当前正式状态、候选比分、来源和采集时间。只有输入精确的 `CONFIRM` 才继续；其他输入均取消且不修改正式数据。

确认过程自动完成：

1. 校验 candidate 与 fixture 的 ID、球队、状态和比分；
2. 在内存中生成 `finished + scores` 的新 fixtures；
3. 在内存中重建并校验 standings；
4. 运行完整 `node --test`；
5. 全部成功后一起写入 fixtures、standings 和候选审核状态。

维护者只判断“这个终场比分可靠吗？”，机械构建和验证由程序完成。

## 冲突、幂等与原子性

- 已 finished 且比分相同：幂等 no-op；不会重复累计积分。
- 已 finished 但比分不同：抛出 conflict，不覆盖正式赛果。
- postponed/cancelled：拒绝直接结算，必须先由可信事实纠正权威状态。
- candidate 球队与 fixture 不一致、比赛不存在、比分非法：拒绝结算。
- 验证或测试失败发生在正式写入之前。
- 三个 JSON 文件先写同目录临时文件；写入中途失败时恢复全部原始字节，避免半完成状态。

## 2026-08-29 mock 回归

测试使用三场正式 fixture 的 ID 与球队结构：常州 VS 无锡、淮安 VS 连云港、扬州 VS 宿迁。测试分数仅存在于内存 mock 中，用于证明三场都能经过 candidate → confirmed → finished 转换；`data/fixtures.json` 没有被写入任何猜测赛果。

## Scope 边界

本阶段没有实现实时比分、轮询、时间推断终场、Webhook、Cron、GitHub Actions 抓取、Canvases API、自动发布、历史赛果回填、公平竞赛积分或抽签逻辑。未来人工录入、官方网页 Adapter、Hermes、VPS Worker 和 Webhook 只需产生同一个 ResultCandidate contract。
